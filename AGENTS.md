# AGENTS.md

Guidance for AI coding agents (Claude Code, Codex, etc.) working in this skill directory.

## What this is

A **Claude Code / OpenCode skill** implemented entirely as Markdown. The runtime artifact is `SKILL.md`: the agent reads its YAML frontmatter (metadata + allowed tools) followed by the editor prompt. There is no build step and no code to run.

This is the **code** humanizer, the companion to the prose `humanizer` skill. Where the prose skill rewrites words, this one rewrites code *style and structure under a hard behavior-preservation constraint*. That constraint is the soul of the skill: any edit to the prompt that weakens it (allowing logic changes, bug injection, silent failure-path changes, or unverifiable rewrites) is a regression.

The skill has **three modes**: the default **auto** one (the `SKILL.md` subtractive pass, then the `HUMAN-SIGNALS.md` injection pass, in a single run), a **clean-only** one (the subtractive pass alone, no injection), and an **additive** one (injection alone, for already-clean code). The auto and additive passes deliberately add formatting and comment entropy, but the behavior-preservation constraint survives intact through the **SAFE/CONDITIONAL/FLAG safety tier**: only provably behavior-neutral (SAFE) or verified-complete (CONDITIONAL) edits are auto-applied; anything that could change behavior or fail to compile (FLAG) is flagged for the human, never written. Weakening that tier (letting a pass auto-apply a FLAG edit, or apply Python indentation/tab changes) is a regression of the same kind as weakening the behavior contract.

## Key files

- `SKILL.md`, the lean entry point (kept under ~250 lines). YAML frontmatter (`name`, `version`, `description`, `license`, `compatibility`, `allowed-tools`) followed by the workflow: modes, the behavior contract and safety tier, how to run (by hand, file by file), the comment voice, calibration, a one-line summary table of the 22 subtractive patterns, the injection pointer, and the reference-file list. **This is the source of truth for the workflow and the mode/scope rules.**
- `PATTERNS.md`, the 22 subtractive patterns (1-22) with Problem/Before/After and a full worked example, loaded when running the subtractive pass. `SKILL.md` carries only the one-line summary table. **This is the source of truth for the subtractive patterns' detail.**
- `HUMAN-SIGNALS.md`, the **injection** track, run by default as auto mode's second phase and alone in additive mode. Holds the injection contract, the SAFE/CONDITIONAL/FLAG safety tier, the per-language whitespace matrix, the H1-H50 catalog, the injection-volume rule, the complete-reference rename checklist, and worked examples. **This is the source of truth for the additive mode.**
- `LANGUAGES.md`, per-language safety detail for the additive track, loaded when injecting into **JavaScript, TypeScript, or C#** (plus shorter C-family / Go-Rust notes). Holds the per-language tier shifts, language-specific human signals, the formatter caveat, and FLAG traps. **This is the source of truth for language-specific tiers.**
- `README.md`, for humans: what it does, installation, usage, style calibration, the subtractive pattern tables, the additive H-track summary, the language coverage, the worked example, and version history.

## The maintenance contract

`SKILL.md`, `PATTERNS.md`, `HUMAN-SIGNALS.md`, `LANGUAGES.md`, and `README.md` must stay in sync. When you change behavior or content:

- **Subtractive patterns:** the **22 numbered patterns** (1-22) are summarized as a one-line table in `SKILL.md` and detailed with Before/After in `PATTERNS.md`. If you add, remove, or renumber any, update the `SKILL.md` summary table, the `PATTERNS.md` detail and its Contents, and the README pattern tables and "N Patterns Detected" heading, all in the same change. Keep numbering stable unless deliberately renumbering.
- **Additive signals:** the injection track defines **50 signals** (H1-H50) in `HUMAN-SIGNALS.md`, grouped into seven categories. If you add, remove, or renumber any, update the README H-track summary table and group ranges in the same change. The `H` namespace is kept separate from the `1-22` namespace on purpose; do not merge them.
- **Language coverage:** `LANGUAGES.md` gives first-class tiers for **JavaScript, TypeScript, C#** (plus C-family / Go-Rust). The per-language tier shifts there must not contradict the safety-matrix row in `HUMAN-SIGNALS.md` or the cross-references in `SKILL.md`/`README.md`. If you add a language or change a tier, update all four. Every tier claim must be true (e.g. "TS type edits are compile-gated CONDITIONAL", "C# `var`↔explicit is SAFE"); a wrong tier that auto-applies a breaking edit is a regression.
- **The behavior contract** (the "The behavior contract" section in `SKILL.md`) and the **injection contract + safety tier** (in `HUMAN-SIGNALS.md`) are the non-negotiable core. Do not soften either. The skill must never trade correctness for "looking human," and the additive track must never auto-apply a FLAG edit.
- **House style and comment voice:** the skill's own prose, and every comment it emits, use no em-dashes and no decorative emoji, and the safety tiers are written as plain text (SAFE/CONDITIONAL/FLAG), never colored-circle emoji. Comments the skill writes or rewrites follow the "Comment voice" section in `SKILL.md` (casual, human, a real dev's working notes), and injection is heavy by default (the **INJECTION VOLUME** rule in `HUMAN-SIGNALS.md`). Reintroducing em-dashes or emoji notation is a regression, and so is making the injected comments formal or making injection light or sparse. The one exception: illustrative emoji inside Before/After examples, which demonstrate the AI tell being removed, stay.
- **Execution invariants:** the model edits each file directly, by hand (Read/Edit/Write), and must never generate a script to transform code (the "Edit by hand, never script it" rule under "How to run" in `SKILL.md`); and it processes every file fully, including human-looking code (the "Cover everything" rule), bounded only by behavior preservation and by not destroying meaning. Reintroducing script-based transformation, or any guidance that tells the model to skip human-looking files or "lean toward leaving code alone," is a regression. The skill also runs at folder and repository scope (the "Running on a folder or repo" section): given a directory it enumerates the first-party source and processes every file, not only when pointed at one file. It works through them one file at a time, fully humanizing each before the next, and must never do a repo-wide single-pattern sweep.
- **Version:** `SKILL.md` frontmatter has a `version:` field and `README.md` has a "Version History" section. Bump both together.
- **Non-obvious fixes:** if you change the prompt to handle a tricky failure mode (a rewrite that changed behavior, a mis-applied idiom), add a short note to the README version history explaining what was fixed and why.

## Editing the prompt files

- Preserve valid YAML frontmatter in `SKILL.md` (formatting and indentation). `HUMAN-SIGNALS.md` and `README.md` carry no frontmatter.
- The prose below the frontmatter is the product. Edit it like a careful instruction document, not code.
- All Before/After examples must be **correct, runnable, and behavior-equivalent on the success path**. If an example intentionally shows a failure-path change (e.g., removing a swallow-all `except`), it must be labelled as such, mirroring what the skill asks its user-facing output to do.
- In `HUMAN-SIGNALS.md`, every catalog row needs a **safety tier** (SAFE/CONDITIONAL/FLAG), and worked examples must (a) stay behavior-equivalent, (b) leave Python indentation/tabs untouched, and (c) show FLAG items as *flagged, not applied*. An example that auto-applies a FLAG edit is a bug in the skill.
- Default example language is **Python**, with **C/C++/Java/JS** used where a whitespace signal needs a brace language. Keep examples idiomatic and minimal.
